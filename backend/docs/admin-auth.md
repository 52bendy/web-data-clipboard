# Admin authentication and access control

REQ-202610-1260 implements the defect-20 fix: the management backend denies
anonymous access by default, including every admin page and every management
API (devices / webhooks / logs / stats / settings). REQ-202610-1269 closes the
defect by adding the deployment requirement and the dedicated regression
matrix below.

## Deployment requirement: the admin surface must remain private

The admin dashboard can read SMS plaintext, rotate the server token and edit
webhooks, so it must never be reachable by the general public. Treat `/admin`,
`/admin/*`, `/api/admin/*` and the management API prefixes as private
infrastructure:

- Keep the built-in login guard enabled. It fails closed when credentials are
  missing; do not add a bypass, and do not serve `backend/public/admin` from a
  separate public static host.
- Deploy behind HTTPS with `ADMIN_USERNAME` and `ADMIN_PASSWORD_HASH` set.
  Before going live, verify that anonymous `GET /admin` redirects to
  `/admin/login` and that anonymous `GET /api/v1/devices` returns `401`.
- A platform-level control (VPN, IP allowlist, reverse-proxy basic auth or a
  private preview domain) is optional defence in depth, never a replacement
  for the application guard.
- This release ships **no public read-only admin view**. If one is ever
  required, build a separate endpoint with an explicit field allowlist and
  sender masking; never expose `/admin` or `/api/admin/*` anonymously.

## Decision: server-side login session

Open question 3 offered login state, HTTP Basic, or a standalone admin token.
This implementation uses a **server-side login session**:

- credentials are exchanged once for an opaque session cookie;
- the cookie is `HttpOnly`, `SameSite=Strict`, `Path=/`, and bounded by
  `Max-Age`; `Secure` is added on HTTPS;
- logout removes the server-side session immediately;
- each session carries its own CSRF token;
- failed logins are limited per client IP and per username.

Basic auth cannot log out or expire a browser session cleanly, and a static
admin token cannot be revoked per session or protected from CSRF. The session
scheme satisfies all three session requirements in the requirement text.

## Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `ADMIN_USERNAME` | `admin` | Administrator login name. |
| `ADMIN_PASSWORD_HASH` | — | Recommended. `scrypt$<salt>$<hash>` generated by the script below. |
| `ADMIN_PASSWORD` | — | Local-development fallback; plaintext in the environment. Ignored when a hash is set. |
| `ADMIN_SESSION_TTL_MS` | `28800000` (8h) | Absolute session lifetime. |
| `ADMIN_LOGIN_MAX_ATTEMPTS` | `5` | Failed attempts allowed per IP and per username in the window. |
| `ADMIN_LOGIN_WINDOW_MS` | `900000` (15m) | Failed-login counting window and lockout duration. |
| `ADMIN_MAX_SESSIONS` | `1000` | In-memory session cap; oldest sessions are evicted first. |
| `ADMIN_COOKIE_SECURE` | `auto` | `auto` adds `Secure` on HTTPS; `true` always; `false` never (local HTTP only). |

Generate a hash:

```sh
node backend/scripts/hash-admin-password.js 'your-strong-password'
# or: printf %s 'your-strong-password' | node backend/scripts/hash-admin-password.js
```

Then start the server with `ADMIN_USERNAME` and `ADMIN_PASSWORD_HASH`. If
neither password source is configured, the admin layer **fails closed**: pages
return 503, `/api/admin/login` returns 503, and management APIs remain 401.

## Protected surface

| Path | Protection |
| --- | --- |
| `/admin/login`, `/admin/login.css` | Public by design (login form only). |
| `/admin`, `/admin/*` | Session cookie required. Anonymous page requests redirect `302` to `/admin/login?next=...`; other methods get `401`. |
| `/api/admin/login` | Public login endpoint (rate limited). |
| `/api/admin/session` | Session required; returns username, expiry and CSRF token. |
| `/api/admin/logout` | Session + CSRF required. |
| `/api/admin/*` (anything else) | Session required; unknown paths return `404` only after authentication. |
| `/api/v1/devices`, `/api/v1/webhooks`, `/api/v1/logs`, `/api/v1/stats`, `/api/v1/settings` | Management prefixes: session required even before the concrete routes land. `X-DCC-Token` alone is not accepted. |
| `/api/v1/health` | Public. |
| `/api/v1/collect`, `/api/v1/clipboard/latest` | Unchanged: `X-DCC-Token` API authentication. |

Future routes can opt into admin protection outside the prefixes with
`{ admin: true }` in the route table passed to `createApp`/`createServer`.

## Cookies and CSRF

Login response:

```http
Set-Cookie: dcc_admin_session=<opaque>; Path=/; HttpOnly; SameSite=Strict; Max-Age=28800
```

- The cookie value is 32 random bytes (base64url); only its SHA-256 digest is
  stored server-side.
- Session fixation is avoided by issuing a fresh token on every login.
- State-changing `/api/admin/*` requests must send `X-CSRF-Token` with the
  value returned by `GET /api/admin/session` (or `POST /api/admin/login`).
- The HTML logout form uses a hidden `_csrf` field instead.
- `SameSite=Strict` blocks cross-site cookie sending; the CSRF token is a second
  layer for same-site XSS-free clients.

## Login failure limiting

Failed attempts increment two fixed-window buckets: `ip:<client IP>` and
`user:<lowercased username>`. The default allows 5 failures per 15 minutes;
the next attempt returns `429` with `Retry-After` (seconds), and a correct
password is also rejected while the bucket is locked. A successful login
clears both buckets. With `TRUST_PROXY=true`, the first `X-Forwarded-For`
address is used and must be written by the trusted proxy.

## Deployment-layer fallback (evaluated)

The application guard is mandatory and self-contained. Platform-level
protection (reverse-proxy basic auth, IP allowlist, VPN, or a private
preview domain) is an **optional defence in depth**, not a replacement:

- keep the admin behind HTTPS; set `TRUST_PROXY=true` only when a trusted
  proxy overwrites `X-Forwarded-Proto` and `X-Forwarded-For`;
- `ADMIN_COOKIE_SECURE=true` can force `Secure` if TLS terminates outside the
  process and forwarded-proto cannot be trusted;
- the in-memory session and login-limiter stores are process-local. A
  multi-instance deployment must use a shared session/limiter store with the
  same interfaces before scaling horizontally.

## Verification

`backend/test/admin-auth.test.js` covers the negative matrix (anonymous pages,
anonymous admin APIs, management prefixes with only `X-DCC-Token`), login
success and cookie attributes, wrong-password generic responses, login
rate-limit lockout and recovery, session expiry, CSRF on logout, fail-closed
configuration, scrypt hash authentication, secure cookies behind HTTPS, path
traversal, security headers and method restrictions.

`backend/test/admin-defect-20.test.js` is the defect-20 regression suite: it
walks every file under `backend/public/admin` (except the login assets) and
asserts anonymous access is denied, covers the sensitive dashboard pages
(dashboard / devices / logs / settings) and management APIs, and proves that a
newly added admin asset is private by default through an isolated static root.
